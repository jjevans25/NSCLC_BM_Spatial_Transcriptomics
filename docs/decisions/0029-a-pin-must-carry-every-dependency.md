# ADR 0029 — A pin must carry every dependency, so the `pip:` section is removed

**Date:** 2026-09-16
**Status:** Accepted
**Task:** P6-T0 (prerequisite to P6-T2, found while planning Phase 6)
**Amends:** ADR 0023 (environments are pinned with `.pin.txt`)
**Related:** ADR 0013 (conda on a path with spaces), ADR 0005 (pinned digests
for data)

## Context

ADR 0023 pinned the three analysis environments with
`<env>.<platform>.pin.txt`, generated by `conda list --explicit --md5` from the
environments that actually produced the committed results. That decision is
sound and stands. **It had one hole, and Phase 6 is the first task that would
have fallen through it.**

`workflow/envs/py-analysis.yaml` declared `rocrate` — the RO-Crate 1.1 builder
P6-T2 needs — under a `pip:` section:

```yaml
  - pip
  - pip:
      - rocrate
```

**`conda list --explicit` records conda packages only.** Verified before the
fix: the deployed `py-analysis` environment carried `rocrate 0.15.1` and
`arcp 0.2.1`, both marked `pypi`, and neither appeared anywhere in
`py-analysis.osx-arm64.pin.txt`.

Snakemake, when a pin file is present, installs **from the pin and ignores the
environment YAML entirely** (`deployment/conda.py:128`). So:

- here, where the environment already existed, `import rocrate` worked;
- in a clean room, the environment would be built from the pin, `rocrate` would
  be absent, and P6-T2 would fail — in the very run whose purpose is to prove
  the pipeline works for someone else.

**This is the same failure shape ADR 0023 was written to close**, one level
down: a pin that looks authoritative and does not describe the environment. The
lock files ADR 0023 deleted were unread and wrong; this pin is read, and
incomplete. A stranger's error message would have been `ModuleNotFoundError`,
with nothing pointing at the `pip:` section as the cause.

It is worth naming how this survived. P6-T2 had never run, so nothing had ever
imported `rocrate` under a pinned environment. **A dependency that no rule
exercises is not pinned, it is merely declared** — and the only check that
would have caught it is the clean-room run, which is scheduled after everything
that depends on it.

## Decision

### 1. `rocrate` moves into the conda dependency list, and the `pip:` section is deleted

conda-forge carries `rocrate 0.15.1` — the exact version pip had installed — so
there is no version change to reason about. With it moved, **`py-analysis` has
no PyPI packages at all** (`conda list | grep -c pypi` → 0), and neither R
environment ever had any. **No dependency in this project can now escape a
pin**, which is the property ADR 0023 believed it had.

### 2. The pin is regenerated by ADDING to the environment that ran, not by re-solving

ADR 0023 §2's load-bearing rule is that a pin describes **what happened**, not
what a fresh solve would produce today. Re-solving `py-analysis.yaml` would have
honoured the YAML and violated that rule: three weeks of conda-forge movement
would have entered the pin as a silent side effect of adding one package.

So the existing `py-analysis` environment was edited in place —
`pip uninstall rocrate arcp`, then
`conda install -c conda-forge rocrate openssl=3.6.3 --freeze-installed` — and
the pin regenerated from it. The `openssl=3.6.3` constraint is there because the
unconstrained install wanted to bump it to 3.6.4; a patch bump that cannot
change a number is still a deviation between the pin and the environment that
produced the results, and it costs nothing to refuse it.

**The resulting pin diff is exactly two added lines**, `arcp` and `rocrate`, and
nothing else in 250 lines changed. That is the whole audit.

### 3. `r-geomx.yaml`'s stale header is corrected in the same commit

It said "Phase 0: GeoMx QC + normalisation"; `p4t2c_export_lr_database` (Phase
4) also runs in it. Editing a comment there fires the software-environment
rerun trigger on every rule in that environment and invalidates its pin, so
`docs/NEXT_STEPS.md` had deferred it to "a commit where that is the point".
**This is that commit** — the transition is being paid once, and bundling the
correction costs nothing rather than a second full transition later.

## Verification

The ADR 0023 transition, run in full:

1. `--conda-create-envs-only` — both changed environments rebuilt **from their
   pins** in 69 s (`py-analysis` → `029d16d9…`, `r-geomx` → `bb226bd9…`).
2. Scoped `-f` on the two `results/interim/env_repair/*.ok` sentinels, re-running
   ADR 0013's repair against the new environment paths. A bare `--forcerun`
   aborts on the `protected()` fetch outputs.
3. `--touch`, 65 of 65 — honest here for ADR 0023 §3's reason: the software did
   not change, only Snakemake's record of which directory it lives in.

Then, because ADR 0013's standing lesson is that a green
`--conda-create-envs-only` is not evidence an environment works, **one rule per
environment was forced to re-execute**: `p3t3_carrier_models` (r-stats, the
mixed-model fit and the most numerically sensitive artifact in the project),
`p4t2c_export_lr_database` (r-geomx) and `p4t7_language_audit` (py-analysis).

**All 119 files in `results/tables/` and `results/figures/` are byte-identical**
to the pre-transition snapshot. The dry run is clean and `--lint` is clean.

## Consequences

- **P6-T2 can be written against `rocrate` with the pin actually carrying it.**
- **The rule generalises: a `pip:` section is incompatible with `.pin.txt`
  pinning.** Any future dependency must come from conda-forge or bioconda, or
  the pinning mechanism has to change — not the other way round.
- ADR 0023's closing line ("regenerating a pin after any env YAML edit is now a
  required step") is necessary but was not sufficient. **The missing half: a
  pin must be regenerated in a way that can represent the edit at all.** A
  `pip:` edit regenerates a pin that silently omits it.
- This does not change the `osx-arm64`-only limitation, which P6-T6 records.
