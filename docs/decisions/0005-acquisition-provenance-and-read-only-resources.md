# ADR 0005 — Two-tier checksums, and `resources/` read-only by filesystem

**Date:** 2026-08-24
**Status:** Accepted
**Task:** P0-T2
**Implements:** PROJECT_PLAN §6 P0-T2 ("Rule must be idempotent and must **not**
re-download if the checksum matches"), CLAUDE.md hard constraint 1

## Context

P0-T2 acquires four artifacts from GEO GSE200563 and records their provenance.
Two things about that turned out not to be self-evident from the code.

### 1. Not every artifact has a stable digest

The task sketch assumed one checksum policy. GEO does not work that way. A HEAD
survey on 2026-08-24 returned:

| Artifact | Bytes | `Last-Modified` |
|---|---|---|
| `GSE200563_processed_data.txt.gz` | 5,130,014 | Mon, 12 Sep 2022 |
| `GSE200563_RAW.tar` | 8,478,720 | Tue, 13 Sep 2022 |
| `filelist.txt` | 9,332 | Tue, 13 Sep 2022 |
| `GSE200563_family.soft.gz` | 8,662 | **Sun, 23 Aug 2026** |

The first three are author-uploaded and have not moved since deposition. The
SOFT family file is **generated by GEO on request** — its timestamp was one day
old at the moment of first download, and it will be different again next time.

Pinning its SHA-256 and hard-failing on mismatch would produce a pipeline that
breaks for reasons having nothing to do with the data, on a schedule nobody
controls. The predictable outcome is that whoever hits it pastes the new digest
in to make the build go green, and after the second or third time that becomes a
reflex. **A checksum you have to keep editing is not a provenance control** — it
is a ritual that trains people to overwrite the thing it exists to protect.

Deleting the SOFT file from the manifest was the alternative. Rejected: it
carries the 120 sample titles and `cell type` values that P0-T3 parses, so it is
required input, and untracked required input is worse than imperfectly tracked
required input.

### 2. `resources/` is read-only, but something has to write it

Hard constraint 1 says no rule, script or notebook writes into `resources/`.
P0-T2 must write into `resources/raw/`. Taken literally the constraint forbids
the task; taken as intended it means **immutable after acquisition**, with the
acquire rule as the single sanctioned writer. Left as prose, the distinction
relies on every future rule author reading CLAUDE.md and agreeing.

## Decision

### Checksums are two-tier, and the tier is declared per artifact

`config.yaml → acquire.artifacts.<name>.stability`, constrained by the config
schema to `fixed | volatile`:

- **`fixed`** — pinned SHA-256, and a mismatch is a **hard failure** that names
  both digests and refuses to continue. These bytes are the data.
- **`volatile`** — the digest is pinned too, but drift **warns and re-records**
  rather than failing. The record then answers "what was there on the day", which
  is the honest claim, instead of "this is guaranteed unchanged", which is not.

The guarantee `volatile` gives up is recovered where it belongs: the SOFT file's
*content* is asserted on by P0-T3 (120 samples, expected AOI-code tally), which
is a stronger check than a digest anyway — it would catch a GEO regeneration that
actually changed the sample set, which is the only kind of change that matters.

An unpinned artifact is reported as `UNPINNED` in `resources/provenance.tsv` and
prints a loud banner, because a `fixed` artifact left `null` is a provenance
control that looks enforced and is not. Same reasoning as
`qc.min_gene_detection_rate`: `null` means unmade, and unmade must not be able to
pass for made.

### Verification lives in the second rule, not the first

`p0t2_fetch_geo` downloads and records; `p0t2_record_provenance` verifies. The
pinned digest is **deliberately not a param of the fetch rule**, because the
digests cannot be known before the first download and must be added afterwards —
and a param change on a rule with `protected()` outputs makes Snakemake mark the
job out of date and then fail trying to overwrite a write-protected file.
Splitting them means adding a pin re-runs only the cheap verification.

Download-time integrity is still checked, against the server's `Content-Length`,
so a truncated transfer fails at the transfer rather than surfacing later as a
confusing digest mismatch. All four sizes matched the independent HEAD survey.

### `resources/` is enforced by the filesystem

Artifact outputs are wrapped in `protected()`. Snakemake chmods them `0444` on
success, so every later rule is mechanically unable to modify them and hard
constraint 1 holds for everything except the rule that creates them.

## Consequences

- **`--use-conda` is now mandatory, not stylistic.** Without it the
  `software-env` rerun trigger fires against the recorded conda stack, the fetch
  jobs are marked out of date, and the DAG build dies with
  `ProtectedOutputException` before doing any work. `snakemake -n` alone is no
  longer a clean dry run. Recorded in CLAUDE.md's useful commands, the rule
  header, and `docs/session-notes.md`, because it is the kind of thing that
  costs an hour when met cold.
- **Re-fetching is deliberately awkward**: `chmod u+w resources/raw/<file> && rm`.
  Editing `acquire_geo.py` triggers the same wall via the `code` trigger. This is
  the intended cost of the guarantee, and it is bounded — the artifacts total
  13 MB and are fetched once.
- **A `volatile` artifact can change without failing the build.** That is the
  deliberate hole. It is covered by P0-T3's content assertions, and it would not
  be covered if the digest were merely being re-pasted by hand each time.
- **The manifest is extensible without touching code.** Adding an artifact is a
  config entry; the wildcard rule and the schema handle the rest. The WTA PKC
  file (needed by `GeomxTools`, absent from GEO — see `docs/data-provenance.md`)
  will land as a `fixed` entry with a non-GEO `base_url` when P0-T5 needs it,
  which is the first case that will test whether one `base_url` per manifest was
  the right shape. It probably is not; expect to move `base_url` per-artifact.
